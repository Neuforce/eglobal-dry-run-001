# Glossary

> **🟩 METHOD — NeuForce standard.** Review optional; propose changes via PR. **Owner:** NeuForce

| Term | Meaning |
|---|---|
| **As-Is** | How the system and processes work today |
| **To-Be** | How they should work in the future solution |
| **Validated As-Is** | An As-Is description where every rule has been checked against the code and approved by humans |
| **Knowledge Unit (KU)** | One business fact, with a source citation, in a standard format |
| **Spike** | A small, timeboxed piece of exploration (e.g. one process) |
| **PRD** | Product Requirements Document: *why* and *what* |
| **SDD** | Spec-Driven Development package: requirements with acceptance criteria → design → tasks. The spec drives agents and developers |
| **AGENTS.md** | A Markdown file with instructions for AI agents. Works with most tools |
| **Skill** | A reusable, step-by-step procedure an agent can run (`skills/<name>/SKILL.md`) |
| **Agent / Subagent** | An AI role with a specific focus (e.g. `auditor`) |
| **MCP** | Model Context Protocol: a standard way to connect an LLM to tools and data (GitHub, Confluence, Drive) |
| **HITL** | Human-in-the-loop: humans approve, correct, or reject what agents propose |
| **Gate** | A checkpoint where a human must approve before the next phase |
| **RULES.md** | Rules learned from human corrections. Agents must follow them |
| **PoC** | Proof of Concept: a minimal working prototype that tests a hypothesis |
| **EARS** | Easy Approach to Requirements Syntax: "When <trigger>, the system shall <response>" |
| **ADR** | Architecture Decision Record |
